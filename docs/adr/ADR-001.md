# ADR-001: Architecture Overview

## Status

Accepted

## Date

2026-07-19

## Context

Escala Livre needs a local-first architecture that supports offline operation, multi-component deployment, and phased delivery across 11 repositories. The system spans backend API, frontend SPA, desktop shell (Electron), activation/licensing subsystem, and supporting infrastructure. Data must persist locally without requiring external services at runtime, while still allowing coordinated updates and deployments across remote origins.

The 11 repositories are organized as:
- **EscalaLivre/contracts** — shared TypeScript types, JSON Schema, OpenAPI spec
- **EscalaLivre/backend** — Spring Boot REST API (Java 21), schedule engine, SQLite + Flyway
- **EscalaLivre/frontend** — React 19 SPA, Vite 6, Tailwind CSS 4
- **EscalaLivre/desktop** — Electron 31 shell, IPC bridge, auto-updater, backend lifecycle
- **EscalaLivre/activation-manager** — Electron app for license issuance, RSA key management, registry sync
- **EscalaLivre/activation-issuer** — Java 21 CLI for JWS RS256 license signing
- **EscalaLivre/activation-registry** — remote-only encrypted registry storage (GitHub/GitLab private repos)
- **EscalaLivre/server** — future server-based deployment (not yet implemented)
- **EscalaLivre/connect** — future sync/connectivity service (not yet implemented)
- **EscalaLivre/mobile** — future mobile app (not yet implemented)
- **EscalaLivre/releases** — release orchestration, ADRs, freeze documentation, audit reports

## Decision

We adopt a **pre-server (local) architecture** where each component runs on the user's machine with CRDT-like registry synchronization across instances.

### Tiered Component Model

The architecture is organized into **4 tiers**, each with distinct responsibility and trust boundaries:

**Tier 1 — Shared Contracts** (`contracts` repository)
- TypeScript type definitions and JSON schemas for all cross-component interfaces
- API request/response types, license payload schemas, event contracts
- Versioned with semver; consumed as npm workspace packages by backend and frontend
- Single source of truth for field names, enumerations, validation rules

**Tier 2 — User-Facing SPA + API** (`backend` + `frontend`)
- Spring Boot backend (Java 21) exposes REST API on `localhost:8087`
- React 19 SPA (Vite 6, TypeScript 5.8, Tailwind 4) served as static assets; communicates via REST over localhost
- Backend manages schedule data, user accounts, RBAC, and operational logic
- Frontend provides schedule visualization, editing, conflict resolution, and export
- 48 REST endpoints across 15 controllers; 15 database tables via 8 Flyway migrations

**Tier 3 — Admin Technical Bridge** (`desktop` + `backend` IPC)
- Electron main process acts as a privileged bridge between OS and backend
- Desktop bridge authenticates to backend via ephemeral bridge secret (see ADR-003)
- Admin operations (user management, license application, system config) routed through this tier
- Electron proxies admin API calls; user-facing calls bypass Electron and go direct from SPA to backend

**Tier 4 — Activation Management** (`activation-manager` + `activation-issuer`)
- Standalone Electron app (activation-manager) handles RSA key management, license issuance, customer/installation tracking, and encrypted registry sync
- activation-issuer (Java 21 CLI JAR) generates JWS RS256 compact signatures; spawned by manager via stdin/stdout
- License metadata synced via encrypted (scrypt + AES-256-GCM) snapshot to private GitHub/GitLab repos
- Never syncs activation keys (compact_jws stays local); CAS-based write with conflict detection

### Dual-Remote Strategy

Git operations use a **dual-remote** configuration:
- **Primary remote**: GitHub (`github.com/EscalaLivre/*`)
- **Fallback remote**: GitLab (`gitlab.com/jf.aschenbrenner/escalalivre-*`)

Each repository has both `origin` (GitHub) and `gitlab` (GitLab) remotes configured. All pushes are made to both remotes for redundancy. GitLab also runs CI pipelines (`.gitlab-ci.yml`) and artifact hosting (generic packages, releases). See ADR-011 for mirror strategy details.

### Stack

| Layer | Technology |
|---|---|
| Desktop shell | Electron 31.7.7 (Chromium, Node.js) |
| Backend API | Spring Boot 3.3.5 (Java 21) |
| Frontend SPA | React 19 + TypeScript 5.8 + Vite 6 + Tailwind 4 |
| Shared contracts | TypeScript + JSON Schema 2020-12 + OpenAPI 3.1.0 |
| Local persistence | SQLite (see ADR-004) |
| License format | JWS / RS256 (see ADR-002) |

## Consequences

**Benefits:**
- Full offline capability — no cloud dependency for core functionality
- Local-first data sovereignty — all user data stays on the machine
- Tiered trust model isolates user operations from admin operations
- Shared contracts prevent type drift across independently deployed components
- Dual-remote provides deployment resilience

**Risks:**
- CAS-based encrypted sync introduces conflict resolution complexity (three-way merge on sync_state)
- Local-only data means no built-in multi-device sync (future enhancement — server/connect repos)
- Electron bundle size increases installer footprint (QA6: 144 MB, RC11: 168 MB)
- 11 repositories require disciplined release coordination
- SQLite concurrent write contention if activation-manager and backend write simultaneously (mitigated by component isolation)

**Trade-offs accepted:**
- We accept operational complexity of 11 repos in exchange for clear component boundaries
- We accept Electron overhead in exchange for cross-platform desktop distribution
- We accept JWS license complexity in exchange for offline-verifiable, tamper-proof licensing
