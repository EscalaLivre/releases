# ADR-003: Communication Protocol

## Status

Accepted

## Date

2026-07-19

## Context

Escala Livre has three runtime components that must communicate locally: the React frontend SPA, the Electron desktop shell, and the Spring Boot backend API. These components run on the same machine with no network exposure, but require security isolation to prevent unauthorized local access and to distinguish between user-level operations and privileged admin operations.

The communication must:
- Work entirely over localhost (no remote endpoints)
- Distinguish between public, user-authenticated, and admin-authenticated requests
- Prevent other local processes from impersonating the desktop application
- Support Electron's IPC model where the main process proxies certain backend calls
- Maintain separation between user-facing calls (SPA direct) and admin calls (Electron-proxied)

## Decision

We adopt **REST over localhost:8087** as the sole communication protocol. All components communicate via HTTP/1.1 JSON requests to `http://localhost:8087`.

### Endpoint Address

The backend binds to `127.0.0.1:8087` (localhost only — no `0.0.0.0` binding). This ensures the API is not accessible from other machines on the network.

### Three Authentication Layers

Every API request falls into one of three authentication tiers:

**Layer 1 — Public (no auth)**
- Health check: `GET /health`
- License verification: `POST /api/activation/verify`
- These endpoints require no authentication token

**Layer 2 — JWT (regular user)**
- All user-facing endpoints (schedules, shifts, reports, profile)
- Client sends `Authorization: Bearer <jwt>` header
- JWT issued by backend after username/password login (see ADR-005)
- 60-minute TTL, validated on each request

**Layer 3 — Desktop Bridge Secret + Admin Session (technical/admin)**
- Admin endpoints (user management, license application, system config, audit logs)
- Requires **two** headers simultaneously:
  - `X-Desktop-Bridge-Secret: <ephemeral-secret>` — proves request originates from the Electron main process
  - `X-Admin-Session: <admin-session-token>` — proves the admin has authenticated via GitHub Device Flow

### DesktopBridgeFilter

A Spring Boot servlet filter (`DesktopBridgeFilter`) intercepts all requests and enforces Layer 3 authentication for admin endpoints:

```
Request → DesktopBridgeFilter
  ├─ Is endpoint in public list? → Pass through (Layer 1)
  ├─ Is endpoint in user list? → Validate JWT (Layer 2)
  └─ Is endpoint in admin list? → Validate bridge secret + admin session (Layer 3)
```

The filter checks:
1. `X-Desktop-Bridge-Secret` header is present and matches the current ephemeral secret
2. `X-Admin-Session` header is present and references a valid, non-expired admin session
3. Both validations must pass; if either fails, return `403 Forbidden`

### Ephemeral Bridge Secret

The Electron main process generates a **cryptographically random ephemeral bridge secret** on each application launch:

- Generated via `crypto.randomBytes(32)` and stored only in Electron main process memory
- Passed to the backend via environment variable or local IPC at startup
- Valid only for the lifetime of the Electron process
- Rotated on every application restart
- Not persisted to disk, not accessible to renderer process, not accessible to other local processes

This prevents other local applications from sending admin requests to the backend — only the running Electron instance knows the current bridge secret.

### Call Routing

**User calls (SPA → Backend):**
```
React SPA → http://localhost:8087/api/*
  └─ Authorization: Bearer <jwt>
```
The SPA makes direct HTTP requests to the backend. No Electron involvement.

**Admin calls (Electron → Backend):**
```
Electron Main Process → http://localhost:8087/api/admin/*
  ├─ X-Desktop-Bridge-Secret: <ephemeral>
  └─ X-Admin-Session: <admin-token>
```
The Electron main process proxies admin API calls. The renderer process triggers admin actions via Electron IPC, which the main process translates to authenticated HTTP requests.

**License verification (any client → backend):**
```
Client → http://localhost:8087/api/activation/verify
  └─ No auth required
```

### Request Flow Diagram

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  React SPA  │────▶│  localhost:8087  │◀────│  Electron Main  │
│  (Renderer) │     │  (Spring Boot)   │     │  (Main Process) │
└─────────────┘     └──────────────────┘     └─────────────────┘
     │ JWT auth          ▲                          │ Bridge Secret
     │ (Layer 2)         │                          │ + Admin Session
     │                   │                          │ (Layer 3)
     └───────────────────┘                          │
                     Direct REST                    │
```

## Consequences

**Benefits:**
- Localhost-only binding eliminates network attack surface
- Ephemeral bridge secret prevents cross-process impersonation
- Three-layer auth model provides clear trust boundaries
- SPA direct-to-backend routing reduces latency for user operations
- Electron proxy pattern keeps admin operations in trusted main process
- Standard REST/JSON — no WebSocket complexity, no custom protocol

**Risks:**
- Port 8087 could conflict with other local services (mitigated by configurable port)
- Bridge secret in memory could be extracted by process memory dumping (acceptable threat model)
- No mutual TLS — relies on OS-level localhost guarantees
- Admin session and bridge secret are separate concerns — two-header design adds complexity
- Electron renderer cannot make admin calls directly (must go through IPC → main process)

**Trade-offs accepted:**
- We accept REST overhead (no WebSocket) in exchange for simplicity and cacheability
- We accept two-header admin auth in exchange for defense-in-depth (bridge + session)
- We accept localhost-only in exchange for zero network exposure
- We accept Electron IPC indirection for admin calls in exchange for renderer isolation
