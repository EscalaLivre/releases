# ADR-004: Database Engine

## Status

Accepted

## Date

2026-07-19

## Context

All Escala Livre components need persistent local storage that works offline, supports schema migrations, handles concurrent reads efficiently, and stores data on the user's machine without external database servers. The system has two primary data consumers — the Spring Boot backend and the activation-manager — each with distinct schema requirements and lifecycle management.

Data must reside in platform-appropriate application directories (`%APPDATA%/escalalivre-*` on Windows, `~/.config/escalalivre-*` on Linux, `~/Library/Application Support/escalalivre-*` on macOS). Each component must own its schema independently to avoid cross-component migration coupling.

## Decision

We adopt **SQLite** as the database engine for all persistent storage. Each component manages its own database file and schema independently.

### Backend Database (Spring Boot)

**Engine stack:**
- `org.flyway:flyway-core` — schema migration management
- `org.xerial:sqlite-jdbc` — JDBC driver for SQLite
- `org.springframework.boot:spring-boot-starter-data-jpa` — data access layer

**Configuration:**
- Database file: `%APPDATA%/escalalivre-backend/escala.db`
- WAL mode enabled (`PRAGMA journal_mode=WAL`) for concurrent read/write
- Connection pool: HikariCP with max 5 connections (SQLite is single-writer)
- Foreign keys enforced: `PRAGMA foreign_keys=ON`

**Flyway Migrations:**

The backend has **8 migration files** (V1 through V8) managing **15 tables**:

| Migration | Tables | Purpose |
|---|---|---|
| V1 | `users`, `roles`, `user_roles` | User authentication and RBAC |
| V2 | `schedules`, `schedule_templates` | Schedule definitions and templates |
| V3 | `shifts`, `shift_assignments` | Individual shift instances and assignments |
| V4 | `departments`, `department_members` | Organizational structure |
| V5 | `audit_logs` | Administrative action audit trail |
| V6 | `license_info`, `feature_flags` | Local license cache and feature toggles |
| V7 | `settings`, `notification_queue` | Application settings and pending notifications |
| V8 | `conflict_rules`, `rotation_patterns` | Schedule conflict detection and rotation logic |

Each migration file is named `V{N}__{description}.sql` and executes in order on first run. Flyway tracks applied migrations in the `flyway_schema_history` table.

**Schema management rules:**
- Migrations are append-only — never modify applied migrations
- New columns added via `ALTER TABLE ... ADD COLUMN`
- Breaking changes require a new migration that creates a replacement table and migrates data
- Each migration includes a checksum; Flyway rejects tampered migrations

### Activation Manager Database (Node.js)

**Engine stack:**
- `better-sqlite3` — synchronous SQLite bindings for Node.js
- Direct SQL (no ORM) for transparency and performance

**Configuration:**
- Database file: `%APPDATA%/escalalivre-activation/activation.db`
- WAL mode enabled
- Foreign keys enforced
- Synchronous mode: `NORMAL` (balance between safety and performance)

**Schema Versioning:**

The activation-manager has **schema v4** with **4 migration steps**:

| Step | Tables/Changes | Purpose |
|---|---|---|
| Migration 1 | `licenses`, `seeds` | Core license storage and seat tracking |
| Migration 2 | `installation_fingerprints` | Machine binding and duplicate detection |
| Migration 3 | `plan_history` | License upgrade/downgrade audit trail |
| Migration 4 | `validation_cache` | Offline verification cache with TTL |

Schema version is tracked in a `schema_version` table:
```sql
CREATE TABLE schema_version (
  version INTEGER PRIMARY KEY,
  applied_at TEXT NOT NULL,
  checksum TEXT NOT NULL
);
```

On startup, activation-manager checks current schema version and applies pending migrations sequentially.

### No Shared Database

Each component owns its database exclusively:
- **Backend** (`escalalivre-backend/escala.db`): schedules, users, shifts, settings
- **Activation Manager** (`escalalivre-activation/activation.db`): licenses, seats, plans

There is no cross-component database access. If components need to share data, they communicate via REST API (see ADR-003). This avoids:
- Migration coupling between components
- Concurrent write conflicts across processes
- Schema version synchronization issues

### Data Directory Structure

```
%APPDATA%/
├── escalalivre-backend/
│   ├── escala.db              # Main database
│   ├── escala.db-wal          # Write-ahead log
│   ├── escala.db-shm          # Shared memory file
│   └── flyway_schema_history/ # Migration tracking
├── escalalivre-activation/
│   ├── activation.db          # License database
│   ├── activation.db-wal
│   └── activation.db-shm
├── escalalivre-desktop/
│   └── preferences.json       # Electron user preferences
└── escalalivre-frontend/
    └── cache/                 # SPA offline cache
```

## Consequences

**Benefits:**
- Zero-install database — SQLite is embedded, no server process required
- Full offline capability — data persists locally without network
- WAL mode provides concurrent reads while writing (single-writer, multi-reader)
- Flyway provides auditable, repeatable schema migrations for the backend
- better-sqlite3 synchronous API simplifies activation-manager error handling
- Per-component database isolation prevents cross-component schema conflicts
- Platform-appropriate data directories follow OS conventions

**Risks:**
- SQLite single-writer constraint limits write throughput (acceptable for local-first use)
- WAL files can grow if checkpointing is not managed (mitigated by auto-checkpoint)
- No built-in replication — data is single-machine only
- better-sqlite3 is a native addon — requires compilation during npm install
- Schema migration errors in production require manual intervention (no rollback in Flyway for SQLite)

**Trade-offs accepted:**
- We accept SQLite write serialization in exchange for zero infrastructure
- We accept per-component databases in exchange for migration independence
- We accept native addon compilation in exchange for synchronous Node.js SQLite access
- We accept no replication in exchange for data sovereignty and simplicity
- We accept manual migration recovery in exchange for zero-dependency deployment
