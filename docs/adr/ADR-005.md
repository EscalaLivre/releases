# ADR-005: Authentication and Authorization

## Status

Accepted

## Date

2026-07-19

## Context

Escala Livre has multiple user types with different access levels: schedule operators (day-to-day users), administrators (system managers), and super administrators (platform owners). Authentication must work fully offline — no cloud identity provider dependency at runtime. The system also needs to authenticate the Electron desktop application itself as a trusted caller to the backend API.

Three distinct trust relationships exist:
1. **User → Backend**: Schedule operators authenticate to access scheduling features
2. **Admin → Desktop → Backend**: Administrators authenticate via GitHub Device Flow for privileged operations
3. **Desktop → Backend**: The Electron main process authenticates as a trusted local caller

## Decision

We implement **three parallel authentication systems**, each serving a distinct trust boundary.

### System 1 — Username/Password JWT (Regular Users)

**Flow:**
```
SPA → POST /api/auth/login { username, password }
  └─ Backend validates credentials
     └─ Returns JWT (60-min TTL)
SPA → Authorization: Bearer <jwt> on all subsequent requests
```

**Credential storage:**
- Passwords hashed with **BCrypt** (cost factor 12)
- Stored in `users` table with columns: `id`, `username`, `password_hash`, `display_name`, `created_at`, `updated_at`
- BCrypt hash format: `$2a$12$<22-char salt><31-char hash>`

**JWT details:**
- Algorithm: HS256 (HMAC-SHA256)
- Secret: Generated随机 on first backend startup, stored in `%APPDATA%/escalalivre-backend/jwt-secret.key`
- TTL: 60 minutes (no refresh token — user re-authenticates after expiry)
- Claims: `sub` (user ID), `roles` (array of role names), `iat`, `exp`

**Login rate limiting:**
- 5 failed attempts → 15-minute lockout for the username
- Lockout tracked in-memory (resets on backend restart — acceptable for local-first)

### System 2 — GitHub Device Flow (Admin Authentication)

**Flow:**
```
Desktop App → POST /api/admin/auth/device
  └─ Returns { device_code, user_code, verification_uri }
  └─ Opens browser to GitHub authorization URL

User → Authorizes on GitHub in browser
  └─ GitHub signals completion

Desktop App → POST /api/admin/auth/token { device_code }
  └─ Backend polls GitHub for token
  └─ Returns admin session token
```

**Purpose:**
- Administrators authenticate via GitHub identity to prove authorization
- No GitHub data is stored — only the fact that the user is a recognized admin
- Admin GitHub accounts are pre-registered in a local configuration file (`admin-accounts.json`)

**Admin session:**
- Stored in Electron main process memory only (not in backend database)
- 60-minute TTL, non-refreshable
- Required for all admin API calls via `X-Admin-Session` header (see ADR-003)

**Admin accounts configuration:**
```json
{
  "admins": [
    {
      "github_id": 12345678,
      "github_username": "admin-user",
      "role": "ADMIN"
    }
  ]
}
```

### System 3 — Desktop Bridge Secret (IPC-to-Backend Trust)

**Flow:**
```
Electron Main Process
  ├─ Generates ephemeral secret on launch: crypto.randomBytes(32)
  ├─ Passes secret to backend via local IPC or env var
  └─ Sends X-Desktop-Bridge-Secret header on admin requests
```

**Purpose:**
- Proves that an admin request originates from the Electron main process (not another local process)
- Combined with admin session token for two-factor admin authentication (see ADR-003)
- Ephemeral — new secret generated on every application launch
- Never stored on disk, never exposed to renderer process

### RBAC Roles

The system implements **Role-Based Access Control** with a strict hierarchy:

```
OWNER > ADMIN > MANAGER > SCHEDULE_EDITOR > VIEWER
```

| Role | Capabilities |
|---|---|
| `OWNER` | Full system control. Can transfer ownership, delete account, manage all licenses. Platform super-admin. |
| `ADMIN` | User management, license application, system configuration, audit log access. Cannot transfer ownership. |
| `MANAGER` | Schedule creation/editing, shift assignment, department management, report generation. Cannot manage users. |
| `SCHEDULE_EDITOR` | Schedule viewing/editing, shift creation, conflict resolution. Cannot manage users or departments. |
| `VIEWER` | Read-only access to schedules, shifts, and reports. No write operations. |

**Role assignment:**
- Default role for new users: `VIEWER`
- Role upgrades require `ADMIN` or higher authorization
- `OWNER` role is assigned to the first user created during initial setup (one per installation)

### Authorization Enforcement

Backend authorization is enforced at two levels:

**1. Filter level (DesktopBridgeFilter + JWT filter):**
- Validates authentication token on every request
- Extracts user identity and roles from token
- Rejects unauthenticated requests to protected endpoints

**2. Service level (method-level checks):**
- `@PreAuthorize` annotations on service methods
- Role hierarchy checked programmatically:
  ```java
  public boolean hasPermission(User user, Permission perm) {
      return user.getRoles().stream()
          .anyMatch(role -> role.getLevel() >= perm.requiredLevel());
  }
  ```

### Offline Operation

All three authentication systems operate fully offline:
- BCrypt password validation requires no network
- JWT signing/verification uses locally-stored secret
- GitHub Device Flow is the only network-dependent step — occurs once during admin login, then the session is local
- Bridge secret is generated and validated locally
- Role checks are local database lookups

## Consequences

**Benefits:**
- Fully offline authentication — no cloud dependency at runtime
- BCrypt provides industry-standard password hashing with salt
- GitHub Device Flow provides strong admin identity verification without custom OAuth infrastructure
- Ephemeral bridge secret prevents local process impersonation
- RBAC hierarchy provides fine-grained access control
- Three-system design cleanly separates user, admin, and IPC trust boundaries
- 60-minute JWT TTL limits exposure window for stolen tokens

**Risks:**
- GitHub Device Flow requires one-time network access for admin login (acceptable — admin login is infrequent)
- BCrypt cost factor 12 adds ~250ms per login attempt (acceptable for local-first)
- No JWT refresh token — users re-authenticate after 60 minutes (acceptable for desktop app)
- In-memory admin sessions lost on Electron crash — admin must re-authenticate
- Role hierarchy is enforced programmatically, not database-constrained — bugs could allow escalation
- No account lockout persistence across backend restarts

**Trade-offs accepted:**
- We accept GitHub network dependency for admin auth in exchange for strong identity verification
- We accept BCrypt latency in exchange for password security
- We accept 60-minute JWT TTL in exchange for no refresh token complexity
- We accept in-memory admin sessions in exchange for no session database overhead
- We accept role hierarchy in code in exchange for flexible role configuration
