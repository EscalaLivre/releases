# ADR-006: Registry Sync (Encrypted Remote Replication)

**Status:** Accepted

**Date:** 2026-07-19

## Context

Activation management requires encrypted off-site backup of customer, installation, and license metadata without exposing activation keys (private JWS tokens). The registry contains sensitive business data that must be replicated to a remote private repository for disaster recovery and multi-node consistency, but private JWS signing keys must never leave the local machine. Without encrypted replication, data loss or corruption of the local registry database would result in permanent loss of license records and customer associations. Conversely, naive replication would risk leaking private JWS tokens, which would allow unauthorized license issuance.

## Decision

We adopt a CAS-based encrypted snapshot sync approach using **scrypt KDF + AES-256-GCM** encryption. The registry is stored in a private GitHub or GitLab repository as a single encrypted file. Conflict resolution uses a three-way merge strategy. The system **never syncs `compact_jws`** — activation keys remain local at all times. A provider-agnostic `RegistryApi` interface abstracts remote operations, with concrete implementations for both GitHub and GitLab.

### ELAMREGISTRY Envelope Format

All synced files use the `ELAMREGISTRY` envelope:

```
ELAMREGISTRY-v1\n
<base64(SHA-256(ciphertext))>\n
<base64(IV)>\n
<base64(ciphertext)>
```

- **IV:** 12-byte random nonce for AES-256-GCM
- **Ciphertext:** AES-256-GCM encrypted JSON payload of registry snapshot
- **SHA-256:** Verification hash computed over the raw ciphertext bytes

### CAS Write with SHA Verification

Each sync push writes a content-addressed blob:

1. Serialize registry snapshot to JSON (excluding `compact_jws` fields)
2. Encrypt payload with AES-256-GCM using derived key
3. Compute SHA-256 of the resulting ciphertext
4. Upload to repository as `snapshots/<sha256>.elamreg`
5. Update the `HEAD` pointer file to reference the new CAS hash

On pull, the client verifies the SHA-256 matches before decrypting, rejecting any tampered blobs.

### Key Derivation

```
key = scrypt(password, salt, N=2^14, r=8, p=1, dkLen=32)
```

Salt is stored unencrypted in the repository metadata. The password is provided by the operator at first sync configuration and cached in the platform keyring (Windows Credential Manager / macOS Keychain).

### Sync State Table

The local `sync_state` table tracks replication state:

| Column | Type | Description |
|---|---|---|
| `key` | TEXT PRIMARY KEY | e.g. `remote_url`, `last_push_generation`, `dirty_generation` |
| `value` | TEXT | Opaque value |

`dirty_generation` increments on every local registry mutation. On sync, if `dirty_generation > last_push_generation`, a push is triggered. On pull, incoming snapshots are compared against local state; three-way merge resolves non-conflicting changes.

### Three-Way Merge

Conflict resolution uses the common ancestor (last shared CAS hash) and applies:

- **Non-overlapping field changes:** Auto-merged
- **Conflicting field changes on same record:** Latest-write-wins based on `updated_at` timestamp
- **Structural conflicts (added/removed records):** Both sides preserved; operator notified

### Automatic Push/Pull

- **On license issuance:** After local commit, check dirty_generation. If ahead, push automatically.
- **On app startup:** Pull latest remote snapshot. If local is behind, merge into local DB.
- **Periodic sync:** Background timer every 5 minutes; pushes if dirty, pulls if remote is ahead.

### Provider-Agnostic RegistryApi

```typescript
interface RegistryApi {
  readSnapshot(ref: string): Promise<ELAMRegistryEnvelope>
  writeSnapshot(envelope: ELAMRegistryEnvelope, message: string): Promise<string>
  getHeadRef(): Promise<string>
  setHeadRef(ref: string, currentRef: string): Promise<void>
  listSnapshots(limit: number): Promise<string[]>
}
```

Implementations: `GitHubRegistryApi` (via GitHub REST API + PAT), `GitLabRegistryApi` (via GitLab API + project token).

## Consequences

### Benefits

- **Security:** Private JWS keys never leave the local machine; encrypted-at-rest in transit and at rest in the remote repo
- **Durability:** CAS-based storage prevents corruption; SHA verification detects tampering
- **Offline-capable:** Local registry is fully functional without network; sync is opportunistic
- **Provider flexibility:** GitHub or GitLab backends without code changes in consuming modules
- **Conflict safety:** Three-way merge handles concurrent multi-node edits gracefully

### Risks

- **Key management:** scrypt password loss means encrypted snapshots are irrecoverable — mitigated by vault export with separate password
- **Merge complexity:** Three-way merge on nested JSON structures may produce unexpected results for deeply divergent registries — mitigated by operator review notification
- **Storage growth:** CAS objects accumulate indefinitely — mitigated by optional garbage collection of orphaned snapshots (manual command)
- **Network dependency for sync:** Push/pull requires network access — by design, the system degrades gracefully to local-only operation

### Trade-offs

- We accept the operational complexity of password-based encryption in exchange for never transmitting JWS private keys
- We accept CAS blob accumulation in exchange for tamper-evident, idempotent writes
- We accept automatic merge with latest-write-wins in exchange for zero-friction multi-node operation
