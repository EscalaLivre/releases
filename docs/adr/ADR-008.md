# ADR-008: Frontend Tech Stack

**Status:** Accepted

**Date:** 2026-07-19

## Context

The frontend SPA needs to be maintainable, performant, and work both inside Electron (with IPC bridge for backend operations) and as a standalone web application (for direct API access during development or alternative deployment). The stack must support TypeScript for type safety, hot module replacement for development velocity, and must not require a server-side rendering infrastructure. Routing must work without a server (important for Electron's `file://` protocol). Admin API calls must be proxied through Electron's IPC bridge, while regular API calls go directly to `localhost:8087`.

## Decision

We adopt **React 19 + TypeScript 5.8 + Vite 6 + Tailwind CSS 4** as the frontend stack. Routing uses a **hash-based SPA router** (no server needed). A **single entry point** detects `window.escalaDesktop` to determine Electron vs. standalone mode. All admin API calls are proxied through Electron IPC; regular API calls go direct to `localhost:8087`.

### Technology Choices

| Layer | Choice | Rationale |
|---|---|---|
| UI Framework | React 19 | Concurrent features, ecosystem maturity, team familiarity |
| Language | TypeScript 5.8 | Strict typing, excellent tooling, shared types with backend |
| Bundler | Vite 6 | Fast HMR, native ESM, optimized production builds |
| Styling | Tailwind CSS 4 | Utility-first, zero-runtime, small bundle |
| Routing | Hash-based SPA router | Works with `file://` protocol, no server config needed |
| State | React Context + hooks | Sufficient for app scope; no external state library needed |

### Hash-Based SPA Router

All routes use `#/path` format:

```
file:///app/index.html#/dashboard
file:///app/index.html#/customers
file:///app/index.html#/licenses
```

The router listens to `hashchange` events and parses the fragment. This avoids any dependency on server-side URL rewriting and works identically in Electron (`file://`) and browser (`http://`).

Route definitions:

| Route | Component | Description |
|---|---|---|
| `#/` | Dashboard | Overview with stats |
| `#/customers` | CustomerList | All customers |
| `#/customers/:id` | CustomerDetail | Customer info + installations |
| `#/installations` | InstallationList | All installations |
| `#/installations/:id` | InstallationDetail | Installation + licenses |
| `#/licenses` | LicenseList | All licenses |
| `#/licenses/:id` | LicenseDetail | License detail + JWS info |
| `#/licenses/issue` | LicenseIssue | Issue new license form |
| `#/registry` | RegistryView | Registry status + sync |
| `#/sync` | SyncView | Sync history + controls |
| `#/audit` | AuditLog | Audit trail viewer |
| `#/settings` | Settings | App configuration |
| `#/about` | About | Version info |

### Mode Detection

The single entry point (`main.tsx`) detects the runtime environment:

```typescript
function isElectron(): boolean {
  return typeof window !== 'undefined' 
    && typeof (window as any).escalaDesktop !== 'undefined'
}
```

- **Electron mode:** API calls go through `window.escalaDesktop.*` IPC bridge. Admin operations (registry, sync, vault) are proxied through the main process.
- **Standalone mode:** All API calls go directly to `http://localhost:8087`. Admin operations are unavailable or hit the local REST API directly.

### API Directory Structure

```
src/
  api/
    client.ts          # Base HTTP client (fetch wrapper)
    types.ts           # Shared API types (mirrors backend models)
    github.ts          # GitHub Device Flow operations
    licenses.ts        # License CRUD + issuance
    customers.ts       # Customer management
    installations.ts   # Installation management
    registry.ts        # Registry operations
    sync.ts            # Sync operations
    audit.ts           # Audit log queries
    electron-bridge.ts # IPC bridge adapter (wraps window.escalaDesktop)
```

`electron-bridge.ts` implements the same interface as the direct HTTP client but routes through IPC:

```typescript
const apiClient = isElectron() 
  ? createElectronBridgeClient() 
  : createHttpClient('http://localhost:8087')
```

All consuming code uses the unified `apiClient` without knowing which transport is active.

### Pages (13)

1. **Dashboard** — Aggregate stats: total customers, installations, active licenses, last sync time
2. **CustomerList** — Paginated table with search, create new customer
3. **CustomerDetail** — Customer info, associated installations, license summary
4. **InstallationList** — Paginated table with customer filter
5. **InstallationDetail** — Installation info, associated licenses, activation status
6. **LicenseList** — Paginated table with status filter (active/expired/revoked)
7. **LicenseDetail** — Full license info, JWS payload viewer (decoded, not raw), installation binding
8. **LicenseIssue** — Multi-step form: select customer → select installation → configure license params → issue
9. **RegistryView** — Registry health, CAS hash, dirty status, sync controls
10. **SyncView** — Sync history log, manual push/pull, conflict resolution UI
11. **AuditLog** — Filterable audit trail with date range and action type filters
12. **Settings** — Backend URL, sync config, GitHub auth status, theme
13. **About** — Version, license, system info

## Consequences

### Benefits

- **Dual-mode runtime:** Same codebase works in Electron and browser without conditional compilation
- **Fast development:** Vite 6 HMR with TypeScript gives instant feedback
- **Minimal runtime:** Tailwind CSS 4 eliminates runtime CSS-in-JS overhead
- **No server dependency:** Hash-based routing works with `file://` protocol in Electron
- **Type safety end-to-end:** TypeScript types shared between frontend API layer and backend models
- **Small bundle:** React 19 + Vite 6 tree-shaking produces compact production bundles

### Risks

- **Hash-based routing limitations:** URLs with `#` are less conventional; no server-side rendering of specific routes — acceptable for a desktop management app
- **Tailwind learning curve:** Utility classes require familiarity — mitigated by consistent design system components
- **React 19 adoption:** Concurrent features are new — mitigated by gradual adoption; core app doesn't require concurrent APIs
- **No offline-first caching:** SPA relies on backend availability — acceptable because backend runs locally on the same machine

### Trade-offs

- We accept hash-based routing in exchange for `file://` protocol compatibility in Electron
- We accept direct `localhost:8087` calls in standalone mode in exchange for zero-overhead API access during development
- We accept Tailwind's utility-first approach in exchange for eliminating runtime CSS-in-JS
- We accept 13 page components in exchange for focused, single-responsibility views
