# ADR-009: Activation Manager Architecture

**Status:** Accepted

**Date:** 2026-07-19

## Context

The activation manager is a standalone Electron application for operational license management. It must be completely offline-capable (no cloud dependency for core operations) and security-hardened (protecting JWS signing keys, customer data, and audit trails). The manager handles the full lifecycle: customer registration, installation binding, license issuance (JWS signing), activation key generation, and registry synchronization. Operators authenticate via GitHub Device Flow, but the application must function fully offline after initial authentication. Backup and export capabilities are required for disaster recovery.

## Decision

We build an **Electron app with React UI**, **SQLite database** (better-sqlite3), **Windows DPAPI-secured RSA key store**, and a **Java-based JWS issuer** (spawned as CLI). The app enforces **single-instance lock**, uses **GitHub Device Flow** for operator authentication (single authorized user), exposes **38 IPC channels**, includes an **auto-backup system**, and enforces **hardened CSP**.

### SecureKeyStore via DPAPI

RSA-4096 key pair for JWS signing, protected by Windows Data Protection API:

```typescript
class SecureKeyStore {
  private keyPath: string
  
  async generateKeyPair(): Promise<void> {
    const { publicKey, privateKey } = crypto.generateKeyPairSync('rsa', {
      modulusLength: 4096,
      publicKeyEncoding: { type: 'spki', format: 'pem' },
      privateKeyEncoding: { type: 'pkcs8', format: 'pem' }
    })
    // Encrypt private key with DPAPI before writing to disk
    const encrypted = dpapi.encryptBuffer(Buffer.from(privateKey))
    fs.writeFileSync(this.keyPath, encrypted)
    fs.writeFileSync(this.keyPath + '.pub', publicKey)
  }
  
  async sign(payload: string): Promise<string> {
    const encrypted = fs.readFileSync(this.keyPath)
    const privateKey = dpapi.decryptBuffer(encrypted).toString()
    return crypto.sign('sha256', Buffer.from(payload), privateKey)
  }
}
```

- Private key is encrypted at rest via DPAPI (tied to Windows user account)
- Key never exists unencrypted on disk
- JWS signing is performed by spawning the Java CLI tool, which receives the payload via stdin and returns the signed JWS via stdout

### JWS Issuer (Java CLI)

The JWS issuer is a standalone Java application invoked as a child process:

```bash
java -jar jws-issuer.jar sign \
  --key /path/to/private-key.pem \
  --header '{"alg":"RS256","typ":"JWT"}' \
  --payload '{"sub":"license-id","iat":1234567890}'
```

- Receives payload via command-line arguments or stdin
- Returns compact JWS string on stdout
- Java chosen for JWS library maturity (nimbus-jose-jwt)
- Spawned process is ephemeral; no long-running Java daemon

### GitHub Device Flow (Single Authorized User)

Operator authentication uses GitHub Device Flow:

1. App requests device code from GitHub
2. Operator visits `github.com/login/device` and enters code
3. App polls GitHub until authorization completes
4. First authorized user becomes the **sole operator** — subsequent authorizations are rejected unless they match
5. Operator identity cached locally; re-authentication required only after token expiry or revocation

### Auto-Backup System

Automatic backup configuration:

```typescript
interface BackupConfig {
  enabled: boolean
  intervalMs: number          // default: 3600000 (1 hour)
  maxBackups: number          // default: 10
  backupDir: string           // default: ~/.elam/backups/
}
```

- On each backup: export full vault (`.elamvault` encrypted archive) to backup directory
- Rotation: when `maxBackups` exceeded, oldest backup deleted
- Backup triggered on: scheduled interval, before registry sync, before vault export, on app shutdown (if dirty)
- `.elamvault` format: AES-256-GCM encrypted ZIP containing SQLite dump + key metadata (no private keys)

## Consequences

### Benefits

- **Offline-capable:** All core operations (license issuance, customer management, registry sync queueing) work without network
- **Security:** DPAPI protects RSA keys at rest; CSP prevents renderer attacks; single-instance prevents data races; sandbox mode isolates renderer
- **Auditability:** Full audit trail of all mutations with actor identification
- **Disaster recovery:** Auto-backup + vault export/import + registry sync provide three layers of data protection
- **Simplicity:** better-sqlite3 synchronous API avoids async complexity; single Java CLI for JWS signing avoids JVM lifecycle management

### Risks

- **DPAPI Windows-only:** Key protection is tied to Windows DPAPI — no cross-platform support without alternative key store (macOS Keychain, Linux Secret Service) — acceptable for current deployment target
- **Java dependency:** JWS issuer requires JRE installed on target machine — mitigated by bundling JRE with installer or using GraalVM native-image
- **Single operator limitation:** Only one authorized GitHub user — acceptable for operational license management use case
- **SQLite concurrency:** better-sqlite3 uses file-level locking — acceptable for single-user desktop app; concurrent multi-user would require migration to client-server DB
- **38 IPC channels:** Significant boilerplate — mitigated by shared type definitions and code generation

### Trade-offs

- We accept Windows DPAPI dependency in exchange for hardware-bound key protection without requiring a separate HSM
- We accept Java CLI spawn overhead in exchange for mature JWS library support and process isolation for cryptographic operations
- We accept single-instance lock in exchange for preventing database corruption from concurrent writes
- We accept single-operator model in exchange for simplified access control and audit trail
- We accept 38 IPC channels in exchange for fine-grained, auditable operations with least-privilege access per channel
