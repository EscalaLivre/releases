# ADR-013: Uso Condicional de Redis

## Status

Accepted

## Date

2026-07-20

## Context

The Escala Livre architecture currently operates fully offline with SQLite persistence. As the system evolves toward server deployment and multi-instance scenarios, distributed state management may become necessary. Redis has been proposed as a potential solution, but its introduction must be justified by proven need rather than speculative requirements.

## Decision (concrete rules)

1. Redis is NOT mandatory initially and must NOT be introduced in Sprint 2 (EL-04)
2. Redis enters the architecture ONLY when a concrete, measured need for one or more of these specific use cases is demonstrated:
   - Distributed HTTP sessions across multiple backend instances
   - Real-time token/activation revocation propagation
   - Device pairing coordination across instances
   - Shared rate limiting across instances
   - Fan-out of events to connected clients
   - Temporary distributed locks for critical sections
3. Each use case must be documented in a dedicated ADR extension with measurable thresholds before requiring Redis
4. Redis NEVER stores authoritative data for: schedules, employees, users, departments, schedule codes, license payloads — these remain in MySQL/SQLite
5. A gate decision must be emitted before production deployment:
   - `REDIS_REQUIRED_NOW`: Redis infrastructure is deployed
   - `REDIS_DEFERRED`: Not yet needed, may be reconsidered later
6. If Redis is deferred, an in-memory fallback (e.g., Caffeine, Guava cache) may be used for local single-instance scenarios

## Consequences

- Avoids premature infrastructure complexity
- Redis dependency is gated by measurable criteria
- In-memory fallback provides adequate performance for single-instance desktop deployments
- Future multi-instance deployments will need to pass the Redis gate before adding infrastructure
